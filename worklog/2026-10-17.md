## 5. 结论与发现
- **单请求 decode 很稳**：4080S Q4_K_M 约 20 tok/s，5090 FP8（SGLang，无投机）约 48–50 tok/s，都不随输入长度明显变化，符合混合架构（48 层线性注意力状态固定，只有 16 层有 KV）。
- **Ollama 对 qwen35 架构不支持并行**：日志 `model architecture does not currently support parallel requests`，实际只开 1 个处理槽；并发 2、4 只是排队，TTFT 随排队位置叠加，总吞吐不涨。
- 混合架构下 Ollama 不复用 prompt 缓存，每次都完整 prefill；首次加载约 115 s，正式压测前必须预热。
- **5090 32GB 上 DSPARK 投机解码不可行**：主模型 + 2.71 GB 草稿模型连权重都放不下。
- **思考开/关不改变输入上限**（拒绝阈值 = 池 − 6），区别在输出：输入 + reasoning + 回答 ≤ 池 − 2；超出时不报错，在 finish=length 处截断，思考可能拿不到最终答案。估算：给 xhigh 留 8192 输出时，C2 输入应 ≤ 约 12.2K，C3 ≤ 约 34.3K。
- **start.sh 的 `--allow-auto-truncate` 会制造假成功**：超长输入被静默截成 25774 tokens、completion 0、HTTP 200。
- **transformers FP8 的 gate_proj 问题是正则未锚定导致的**（PR #47990），打补丁后官方 FP8 在 5090 上完全可用，可以直接做逐层 hook 抓取；单次前向上限 7168 token。
- 选型建议（调研结论）：生成和提取分开做，生成用 vLLM/SGLang，提取用 transformers + 官方 FP8 teacher-forced 前向；GGUF Q8_0 + llama.cpp 作独立交叉验证；比较向量时用 debiased CKA，并同时报告 Procrustes。

## 6. 踩坑记录
- 远程执行 `pkill -f 'ollama serve'` 会连带杀掉 SSH 会话本身，改用脚本按进程名精确停止。
- PowerShell 会在本地展开双引号里的 `$(...)`，远程命令要避开 `$` 或改为上传脚本执行。
- raw 模式下模型很早就输出 EOS（只生成 46 到 114 tokens），改为非 raw 加长文提示后能稳定生成满 256 tokens。
- 中文文件名经 PowerShell 管道传输会乱码，改用 base64 传输。
- flashinfer JIT 在系统 CUDA 12.8 下报 `FlashInfer requires GPUs with sm75 or higher`，设 `FLASHINFER_CUDA_ARCH_LIST=12.0a` + `CUDA_HOME=/usr/local/cuda` 解决（首次 JIT 114 s）；改用 pip 的 CUDA 13.3 nvcc 会报头文件不兼容。
- SGLang 省显存必须加 `--mm-feature-transport cpu` 和 `--disable-fast-image-processor`（否则首次请求额外建约 604 MiB CUDA 上下文导致 OOM）。
- 把架构改成 `Qwen3_5ForCausalLM` 的 text-only 视图看似能启动，实际一个层权重都没加载，输出全是 "!!!!"；`vision_config.depth=0` 会让 ViT cuda-graph runner 报 IndexError，用 depth=1。novis 视图下图像输入不可用。
- start.sh 的草稿模型路径不存在，`/root/model_dspark/model.safetensors` 是悬空符号链接。
- transformers 的 FP8 kernel 要从 HF Hub 下载，服务器访问不到 huggingface.co，设 `HF_ENDPOINT=https://hf-mirror.com` 解决（未开 trust_remote_code）。
- 只 patch `quantizers_utils` 不够，`finegrained_fp8` 在 import 时已绑定函数，补丁需打到 5 个命名空间。
- 空载时 nvidia-smi 显示 GPU-Util 100%（0 MiB、无进程）；服务器时钟比 box 慢约 6 分钟。
